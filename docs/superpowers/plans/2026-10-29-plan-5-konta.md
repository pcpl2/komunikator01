# Plan 5: konta z zaproszeniami, CLI admina, zapamiętana sesja — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Friends join with one pasted invite code, pick their own login and password, and stay logged in through a refreshable session token; the admin manages invites, accounts and rooms from `komunikator-server` subcommands.

**Architecture:** Accounts, invites and session tokens move into the existing SQLite database (`data_dir/komunikator.db`); users from the old `[[users]]` config section are imported once. `Hello` carries an `Auth` (password, token, or register-with-invite); every successful login returns a fresh single-use token, which the client stores DPAPI-protected instead of the password. An invite is one copy-paste string bundling the server address, certificate fingerprint and a one-time code. Admin subcommands open the same database directly (WAL mode); the running server re-reads blocked accounts and rooms every 5 s and acts on changes.

**Tech Stack:** Rust 2021, rusqlite (bundled, already present), argon2 (present), sha2, getrandom, clap; no new crates.

**Spec:** `docs/superpowers/specs/2026-10-28-komunikator-glosowy-design.md` — sections 6.5 (accounts), 6.6 (rooms, admin deletes), 6.8 (server: SQLite, login rate limit, journald, no content in logs), 6.9 (first configuration: server address + invite code).

## Global Constraints

- Passwords are stored only as Argon2id hashes; the password is used only to log in and never relates to E2E keys (spec 6.5).
- Registration only with an invite code generated by the admin; no e-mail (spec 6.5).
- Admin = whoever has shell access to the server; management through server CLI subcommands (spec 6.5).
- The client remembers the session with a refreshed token so players do not log in at every start (spec 6.5).
- Login attempts are rate-limited (existing `LoginLimiter`) — registration and token logins count as attempts too (spec 6.8).
- Logs never contain passwords, tokens, invite codes or chat content (spec 6.8).
- Tokens and invite codes are stored on the server only as SHA-256 hashes; on the client the token is DPAPI-protected like the password today.
- Wire format: append-only variant order; `Hello` stays variant 0 with `version` first; `PROTOCOL_VERSION` becomes 4.
- All user-facing text in Polish with correct diacritics.
- No new crates.

## Review Focus

1. Two friends redeem the same invite at the same moment → exactly one account is created; the other gets `InviteInvalid` (Task 2 `invite_is_single_use_under_race`).
2. A stolen old token after the player logged in again → every successful login rotates the token and a used one stops working (Task 2 `token_login_works_once_and_rotates`).
3. The admin blocks an account that is online → it is disconnected within 10 s and cannot log in with password or token (Task 3 `blocked_online_user_is_kicked`).
4. A username that differs only by case or Unicode tricks from an existing one ("Ala" vs "ala", or with a bidi control) → rejected as taken or invalid (Task 1 `usernames_are_unique_and_clean`).
5. A server started with the old config `[[users]]` → those accounts keep working with their passwords, no manual migration (Task 1 `config_users_are_imported_once`).

  - `invites(code_hash BLOB PRIMARY KEY, created INTEGER NOT NULL, expires INTEGER NOT NULL, used_by TEXT)`

  - `fn create_invite(&self, code: &[u8; 16], now: u64, ttl_s: u64) -> anyhow::Result<()>`; `fn register(&self, code: &[u8; 16], name: &str, hash: &str, now: u64) -> Result<Account, RegisterError>` — one immediate transaction: invite exists, unused, not expired → mark used, insert account; `pub enum RegisterError { InviteInvalid, NameTaken, Db(anyhow::Error) }`.

  - `fn set_password(&self, name: &str, hash: &str) -> anyhow::Result<bool>` (also revokes tokens); `fn set_blocked(&self, name: &str, blocked: bool) -> anyhow::Result<bool>` (blocking revokes tokens); `fn set_admin(&self, name: &str, admin: bool) -> anyhow::Result<bool>`; `fn blocked_accounts(&self) -> anyhow::Result<Vec<String>>`; `fn accounts(&self) -> anyhow::Result<Vec<Account>>`; `pub struct InviteInfo { pub created: u64, pub expires: u64, pub used_by: Option<String> }`, `fn invites(&self) -> anyhow::Result<Vec<InviteInfo>>` (never the code); `fn import_config_users(&self, users: &[UserEntry], now: u64) -> anyhow::Result<usize>` — inserts missing accounts with their existing hash and `admin` flag, skips existing ones.
  - Codes and tokens are stored only as SHA-256 hashes.
- `ServerConfig.users` stays optional and is imported at start; `server.example.toml` explains that new accounts come from invites, and gains an optional `public_address = "serwer.example.pl:7700"` (used by Task 3).

### Task 2: Protocol v4 authentication

**Files:** Modify `crates/protocol/src/control.rs`, `crates/protocol/src/lib.rs`, `crates/server/src/conn.rs`, `crates/server/src/lib.rs`, `crates/server/src/auth.rs`; Modify `crates/server/tests/*.rs`, `crates/client-core/tests/common/mod.rs` and the session's `Hello` construction (compile adaptation with `Auth::Password`; Task 4 adds the rest), `crates/client-win` callers as needed to compile.

**Interfaces:**
- Consumes: Task 1 store API.
- Produces (wire, `PROTOCOL_VERSION = 4`):
  - `ClientMsg::Hello { version: u16, username: String, auth: Auth, session: u64, room: RoomChoice }` (still variant 0, `version` first).
  - `pub enum Auth { Password(String), Token([u8; 32]), Register { invite: [u8; 16], password: String } }` (`Debug` written by hand, redacting secrets).
  - `ServerMsg::Welcome { you, room, rooms, members, token: [u8; 32] }` — a fresh session token on every successful login.
  - `RejectReason` appended after `RateLimited`: `InviteInvalid`, `NameTaken`, `NameInvalid`, `AccountBlocked`, `TokenInvalid`, `PasswordTooShort`.
  - consts `TOKEN_TTL_S: u64 = 90 * 24 * 3600`, `MIN_PASSWORD_CHARS: usize = 8`, `CLOSE_BLOCKED: u32 = 3` (server close code).
- Server rules:
  - Every auth kind first passes `LoginLimiter` exactly like today (count before verifying; forgive on success).
  - `Password`: Argon2 verify against the account (dummy hash for unknown names, as today); a blocked account → `AccountBlocked`, reported only after a correct password.
  - `Token`: `redeem_token` must return the account whose `name_key` equals `username.to_lowercase()` and that is not blocked; otherwise `TokenInvalid`.
  - `Register`: `normalize_username` (else `NameInvalid`), password ≥ `MIN_PASSWORD_CHARS` chars (else `PasswordTooShort`), Argon2 hash under the existing concurrency semaphore, then `Store::register` (`InviteInvalid` / `NameTaken`).
  - On success: random token → `issue_token` → sent in `Welcome`. Store calls run in `spawn_blocking`.
  - Blocking: a server task re-reads `blocked_accounts()` every 5 s and closes connections of blocked accounts with `CLOSE_BLOCKED`.
  - `start` imports config users (Task 1); the in-memory `users` map and `admins` set are replaced by store lookups (`admin` flag from the account).
  - Logs: login outcomes with name and reason, never password, token or invite.

### Task 3: Admin CLI and invite strings

**Files:** Create `crates/protocol/src/invite.rs`; Modify `crates/protocol/src/lib.rs`, `crates/server/src/main.rs`, `crates/server/src/lib.rs`, `crates/server/src/conn.rs` (room refresh), `README.md`.

**Interfaces:**
- Produces (protocol): `pub struct Invite { pub server: String /* host:port */, pub fingerprint: [u8; 32], pub code: [u8; 16] }`; `pub fn encode_invite(i: &Invite) -> String` → `"kom1-"` + Crockford base32 (uppercase, no padding, groups of 5 joined by `-`) of `[len(server) u8][server utf8][fingerprint][code][crc16-ccitt of the preceding bytes, big-endian]`; `pub fn decode_invite(s: &str) -> Result<Invite, InviteError>` (case-insensitive; ignores `-`, spaces and newlines; maps `O`→`0`, `I`/`L`→`1`); `pub enum InviteError { Format, Checksum }`. The server address is at most 253 bytes.
- Produces (server CLI subcommands; each takes `--config <path>` to find `data_dir` and opens the database directly):
  - `invite [--days 7] [--server host:port]` — creates a code and prints the invite string; the address comes from `--server`, else `public_address`, else a Polish error explaining what to set. Then prints Polish instructions for the friend (paste the code in `Mam zaproszenie`).
  - `users` (name, admin, blocked, created), `invites` (created, expires, used_by — never codes).
  - `block <name>`, `unblock <name>`, `make-admin <name>`, `revoke-admin <name>`.
  - `reset-password <name>` — reads the new password from stdin, minimum 8 chars, revokes tokens.
  - `rooms`, `create-room <name>`, `delete-room <id>`.
  - `hash-password` stays.
  - The fingerprint comes from `data_dir/cert.der` (same function `start` uses).
- Running server: the 5 s watcher also re-reads rooms. New rooms → `RoomCreated` to everyone; removed rooms → members moved to no room (`MemberMoved` to everyone, announces cleared) then `RoomDeleted`.
