# Plan 2 — Szyfrowanie end-to-end (głos)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serwer przekazuje wyłącznie zaszyfrowany dźwięk, którego nie umie odczytać ani podrobić; klucze uzgadniają między sobą klienci, a każdy klient ostrzega o nieznanych i zmienionych kluczach znajomych.

**Architecture:** Cała kryptografia siedzi w nowym module `client-core::e2e` jako logika bez wejścia/wyjścia (sans-IO): tożsamość urządzenia, podpisane ogłoszenia, magazyn zaufania (TOFU), kanały parami Noise KK, klucze nadawcy z epokami i szyfrowanie ramek audio. Stan `E2e` żyje w zadaniu sesji (wątek sieciowy): ramki Opus z wątku przechwytywania są tam szyfrowane, a przychodzące odszyfrowywane przed buforem jittera — wątki audio się nie zmieniają. Serwer dostaje dwie nowe, nieprzezroczyste dla niego wiadomości (`Announce`, `Relay`) i przekazuje datagramy z epoką.

**Tech Stack:** jak w planie 1, plus `snow` (Noise, domyślny resolver: 25519/ChaChaPoly/BLAKE2s), `ed25519-dalek` (podpisy), `chacha20poly1305` (AEAD ramek), `hkdf` + `sha2` (wyprowadzanie kluczy), `getrandom` (losowość). Wersje: najnowsze wzajemnie zgodne — przed dodaniem sprawdzić dokumentację (Context7) i wybrać zestaw, który kompiluje się razem; klucze tworzyć z bajtów z `getrandom` (`SigningKey::from_bytes`), żeby nie wiązać się z wersją `rand_core`. Windows: DPAPI (`CryptProtectData`, feature `Win32_Security_Cryptography`).

**Spec:** `docs/superpowers/specs/2026-10-28-komunikator-glosowy-design.md` (sekcja 6.3).

**Poza zakresem:** szyfrowanie czatu (plan 3 — czat dostanie własny klucz wyprowadzony z tego samego klucza nadawcy), wiele pokoi (plan 3; tu pokój ma stały numer `0`), rejestr kluczy urządzeń na serwerze przy koncie (plan 4, SQLite — serwer z tego planu niczego nie zapisuje), interfejs graficzny ostrzeżeń (plan 3; tu CLI).

## Global Constraints

- Prymitywy wyłącznie z audytowanych bibliotek (`snow`, RustCrypto, `ring`); żadnej własnej kryptografii niskiego poziomu.
- Model zagrożenia: **serwer potencjalnie wrogi**. Nie może: odczytać dźwięku, podrobić ramki innego nadawcy, dodać „ducha”, któremu klient wyśle klucz, podmienić klucza znajomego bez ostrzeżenia.
- Tożsamość urządzenia: Ed25519 (podpis) + X25519 (Noise) + losowy identyfikator urządzenia 16 B; plik chroniony DPAPI w `%APPDATA%\komunikator\identity.bin`.
- Kanały parami: `Noise_KK_25519_ChaChaPoly_BLAKE2s`, wiadomości przez serwer (`Relay`).
- Klucz nadawcy: 32 losowe bajty na epokę (`u16`); klucz audio = HKDF-SHA256(klucz nadawcy, info `"komunikator/audio/v1"`).
- Ramka audio: `ChaCha20-Poly1305`, AAD = `[kind][sender u16][epoch u16][seq u32]`, nonce = `seq` (LE) dopełniony zerami do 12 B; nadawca nigdy nie używa tego samego `seq` dwa razy pod jednym kluczem.
- Rotacja przy każdym wejściu i wyjściu osoby; nadawca przełącza się na nowy klucz po **500 ms**; odbiorca akceptuje poprzednią epokę jeszcze **2 s** po pierwszej poprawnej ramce nowej.
- Odrzucanie powtórzeń: okno 64 ramek na (nadawca, epoka).
- Klucz nadawcy trafia wyłącznie do osób z ważnym podpisanym ogłoszeniem, których klucz nie jest w stanie „zmieniony, niezaakceptowany”.
- CBR zostaje (rozmiar pakietu nie zdradza treści). Szyfrowanie/deszyfrowanie w wątku sieciowym — wątki audio bez zmian, bez alokacji.
- `PROTOCOL_VERSION = 2` (zmienia się format datagramów i wiadomości).
- Serwer nie loguje zawartości `Announce`/`Relay`.
- Protokół opisany krótko w `docs/e2e.md`.

## Review Focus

1. **Szybkie wejścia/wyjścia w trakcie mowy** (ktoś łączy się ponownie dwa razy w ciągu sekundy) — dźwięk wraca najpóźniej ~1 s po ostatniej zmianie, nikt nie zostaje „głuchy” na stałe. Test: Task 7 `rapid_churn_converges`.
2. **Ponowne połączenie jednego klienta** (nowe `MemberId`, nowa sesja Noise, stara musi zniknąć) — po powrocie słyszy i jest słyszany. Test: Task 8 `audio_flows_after_reconnect`.
3. **Zegar znajomego przestawiony o kilka minut** — ogłoszenie nadal przyjęte (okno ±1 h), a nie cicha blokada. Test: Task 3 `announce_tolerates_clock_skew`.
4. **Wrogi serwer**: podrobione / cudze ogłoszenie z inną nazwą, `Relay` z podmienionym `from`, datagram z podmienionym nadawcą lub epoką, powtórzony datagram. Testy: Task 3 `forged_announce_rejected`, `name_mismatch_rejected`; Task 5 `tampered_header_fails`, `replay_rejected`; Task 7 `ghost_gets_no_key`, `relay_from_wrong_member_ignored`.
5. **Plik tożsamości nie do odczytania** (reinstalacja Windows, inny użytkownik — DPAPI nie odszyfruje) — klient nie pada i nie podmienia tożsamości po cichu: stary plik → `identity.bin.broken`, nowa tożsamość, wyraźny komunikat. Test: Task 9 `unreadable_identity_is_set_aside`.

### Task 7: Maszyna stanów pokoju `E2e`

**Files:**
- Create: `crates/client-core/src/e2e/group.rs`

**Interfaces:**
- Consumes: Tasks 3–6.
- Produces:
  - `pub enum E2eEvent { Member { id: MemberId, name: String, trust: Trust, code: String }, Rejected { id: MemberId, reason: AnnounceError } }`
  - `#[derive(Default)] pub struct Output { pub send: Vec<ClientMsg>, pub events: Vec<E2eEvent> }`
  - `pub struct E2e` — `new(identity: Arc<Identity>, trust: Arc<Mutex<KnownDevices>>, me: MemberId, my_name: String, members: &[MemberInfo], next_epoch: u16, now: Instant, now_ms: u64) -> (Self, Output)` — `Output` zawiera własne `Announce`; tworzy klucz nadawcy epoki `next_epoch`.
    - `member_joined(&mut self, m: &MemberInfo, now) -> Output` i `member_left(&mut self, id, now) -> Output` — obie robią **rotację**: nowy klucz `epoch + 1`, rozsyłany do gotowych kanałów; przełączenie pieczętowania po 500 ms (w `tick`). `member_left` usuwa kanał i `AudioOpener` tej osoby.
    - `announce(&mut self, from, blob, now, now_ms) -> Output` — weryfikacja (nazwa z listy członków); zła → `Rejected`, osoba bez kanału; dobra → `Trust` z `KnownDevices`, zdarzenie `Member`, kanał `PairChannel` (inicjator wysyła `Hello1`).
    - `relay(&mut self, from, blob, now) -> Output` — do kanału `from` (brak kanału = ignoruj); gdy kanał właśnie stał się gotowy → wysyła mu bieżący klucz (i nowy, jeśli rotacja czeka); `Inner::SenderKey` → `AudioOpener` nadawcy.
    - `trust_changed(&mut self, id) -> Output` — po `accept`/`verify` w `KnownDevices`; osoba z `KeyChanged` dostaje kanał/klucz dopiero po akceptacji.
    - `tick(&mut self, now) -> Output` — przełącza pieczętowanie na oczekujący klucz po 500 ms.
